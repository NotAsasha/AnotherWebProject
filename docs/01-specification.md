# Етап 1. Специфікація ContaminantMigration

Статус: базові рішення для реалізації. Це специфікація майбутньої поведінки,
а не опис уже реалізованих можливостей. Дата: 2026-11-09.

## 1. Обсяг першої версії

Навчальна платформа моделює перенесення і дифузію домішки у двовимірній області.
Користувач реєструється, задає параметри, запускає задачу, бачить прогрес,
скасовує виконання і переглядає збережені результати на карті концентрації.

Платформа залишається на .NET 10 (`net10.0`), як у поточному репозиторії.
Frontend: Vue 3, TypeScript, Pinia, Tailwind CSS, Vite, Canvas, SignalR.
Використання можливостей конкретної версії C# визначається SDK .NET 10;
обмеження на C# 13 не запроваджуємо.

Обов'язкові можливості з WebProject.txt: серверні обмеження складності,
прогрес, історія, скасування, авторизація, обмеження кількості задач і
балансування між принаймні двома серверами застосунку.
Додаткові можливості: оцінка часу в черзі, автоматичний запуск обмеженої
кількості Worker, адміністративний моніторинг. HTTPS включаємо до базового розгортання.

До першої математичної версії не входять змінні поля швидкості, перешкоди,
реакції, неперервні джерела, 3D і неявні схеми. Початкова пляма моделює
одноразовий викид. Додавання джерела в часі потребуватиме окремого контракту.

## 2. Математична модель

Область: 0 <= x <= Lx, 0 <= y <= Ly; час: 0 <= t <= T.

Рівняння для сталої швидкості (ux, uy) і сталого D:

```text
∂C/∂t + ux ∂C/∂x + uy ∂C/∂y = D (∂²C/∂x² + ∂²C/∂y²)
```

Одиниці: x, y, Lx, Ly, sigma — метри; t — секунди; ux, uy — м/с;
D — м²/с; C — мг/м³. Це горизонтальний зріз із концентрацією на одиницю
об'єму; інтеграл C dx dy не називаємо повною масою без заданої товщини шару.

Початкова умова у внутрішніх вузлах:

```text
C(x,y,0) = peak * exp(-((x-centerX)² + (y-centerY)²)/(2*sigma²))
```

На всіх чотирьох межах C = 0 при будь-якому t, включно з t = 0.
Межові значення мають пріоритет над формулою плями. Це умова Діріхле:
область може втрачати домішку через межі; збереження інтеграла тут не гарантуємо.
Інтерфейс має пояснювати вплив меж і чисельної дифузії Upwind.

Nx і Ny — кількість вузлів, включно з межами. dx = Lx/(Nx-1), dy = Ly/(Ny-1).
Використовуємо явний Euler у часі, Upwind першого порядку для адвекції
і центральні різниці другого порядку для дифузії.

```text
Dx(Cij) = (Cij - C[i-1,j])/dx, якщо ux >= 0;
          (C[i+1,j] - Cij)/dx, якщо ux < 0.
Dy(Cij) — аналогічно за знаком uy.

Cnext[i,j] = C[i,j] + dt * (
  -ux*Dx(Cij) - uy*Dy(Cij)
  +D*((C[i+1,j]-2*Cij+C[i-1,j])/dx²
     +(C[i,j+1]-2*Cij+C[i,j-1])/dy²))
```

Розрахунок: double, два буфери; оновлення лише з попереднього шару.
Не обрізати від'ємні значення мовчки: значущі порушення невід'ємності або
нечислові значення є чисельною помилкою. Допуск визначається чисельними тестами.

### Спільна умова стійкості

Для обраної явної схеми достатня умова невід'ємності коефіцієнтів:

```text
a = |ux|/dx + |uy|/dy + 2*D*(1/dx² + 1/dy²)
dt * a <= 1
```

Це спільне обмеження: перевіряти адвекцію та дифузію окремо недостатньо.
Для автоматичного кроку використовуємо запас 0.9: N = ceil(T*a/0.9),
не менше 1; фактичний dt = T/N. Якщо a = 0, N = 1.
При явно заданому timeStepSeconds: спочатку перевіряємо dt*a <= 1,
далі N = ceil(T/dt), фактичний dt = T/N. Нестійкий запит відхиляємо,
не змінюючи параметри мовчки. Фінальний час завжди T.
Усі похідні величини перевіряються на скінченність і переповнення до
перетворення N в ціле та до виділення пам'яті.

### Демонстраційний набір

Lx = Ly = 100 м; Nx = Ny = 101; ux = 0.5 м/с; uy = 0.1 м/с;
D = 0.1 м²/с; T = 60 с; peak = 1 мг/м³; center = (25,50) м;
sigma = 5 м; автоматичний крок. a = 1 с⁻¹, N = 67, dt ≈ 0.895522 с.
Початковий центр переноситься в напрямку (ux,uy), пляма розмивається.

Довідкові матеріали:
- [FDM: advection-dominated equations](https://hplgit.github.io/fdm-book/doc/pub/book/sphinx/._book012.html).
- [TU Delft: advection–diffusion](https://mude.citg.tudelft.nl/book/2026/numerical_methods_for_PDEs/advection_diffusion_eq.html).
Спільна умова вище отримується з коефіцієнтів саме зафіксованого 2D-оновлення.

## 3. Валідація та початкові ліміти

Значення нижче — конфігуровані стартові обмеження для навчального середовища.
Після бенчмарків етапу 3 їх уточнюємо; це не обіцянка швидкості виконання.

| Параметр | Правило |
|---|---|
| Lx, Ly | 0 < значення <= 10 000 м |
| Nx, Ny | Цілі, від 3 до 512 |
| ux, uy | Від -100 до 100 м/с |
| D | Від 0 до 100 м²/с |
| T | 0 < T <= 86 400 с модельного часу |
| timeStepSeconds | null для auto або скінченне > 0; умова стійкості |
| peak | 0 <= peak <= 1 000 000 мг/м³ |
| centerX, centerY | Строго всередині області |
| sigma | >= max(dx,dy), <= min(Lx,Ly)/2 |
| N | <= 10 000 кроків |
| Оцінка роботи | checked(Nx * Ny * N) <= 200 000 000 оновлень |
| Час виконання | До 60 с реального часу на спробу; очікування в черзі не враховуємо |
| Кадри | Ціле requestedFrames від 2 до 32 |
| Результат | До 32 MiB незжатих Float32-даних на задачу |
| Робочі дані solver | До 64 MiB для двох double-буферів і Float32-кадрів; без метаданих об'єктів |
| Активні задачі користувача | До 3, включно з Queued/Running/Cancelling |
| Задачі користувача загалом | До 100, включно з історією; звільнення через видалення завершених |
| Активні задачі системи | До 100 |
| Конкурентність Worker | 1 задача на екземпляр; початково 2 Worker |

Усі числові поля мають бути скінченними. Сервер повторно перевіряє все,
навіть якщо frontend уже виконав перевірку. Core обчислює похідні параметри;
FluentValidation перевіряє форму запиту й перетворює помилки у відповідь API.
Ліміти кількості задач перевіряються атомарно в PostgreSQL, а не локально в API.
Оцінка пам'яті включає обидва double-буфери й кадри; завершені задачі обмежені
лімітами кількості та розміру. Дискова квота і очищення визначаються перед розгортанням.

## 4. Життєвий цикл задачі

```text
Queued -> Running -> Completed
Queued -> Cancelled
Running -> Cancelling -> Cancelled
Running -> Failed | TimedOut
Cancelling -> Failed | TimedOut
Running -> Queued   (відновлення після втрати Worker, за наявності спроб)
```

Completed, Cancelled, Failed, TimedOut — остаточні стани.
Запит скасування активного обчислення спершу переводить задачу в Cancelling;
Worker підтверджує Cancelled після припинення роботи. Core перевіряє токен
на кожному часовому кроці та між блоками рядків.
Скасування зберігається в БД; повідомлення прискорює його доставку,
періодична перевірка БД забезпечує відновлення при втраті повідомлення.

Фіналізація і скасування використовують перевірку версії запису:
якщо Completed уже збережено — скасування не змінює результат;
якщо Cancelling збережено першим — завершення не може встановити Completed.
Не видаємо CancellationToken локального API за механізм розподіленого скасування.

Доставка повідомлень — щонайменше один раз. Захоплення задачі атомарне,
зі строком оренди, heartbeat і номером спроби як fencing token.
Дублі активної спроби не запускають друге обчислення. Після втрати оренди
старий Worker не може зберегти результат. Не більше 2 обчислювальних спроб;
чисельні помилки й тайм-аут автоматично не повторюємо. Cancelling після втрати
Worker завершується Cancelled, а не повторним запуском.
Точні інтервали оренди та heartbeat налаштовуються на етапі 5.

Прогрес = завершені кроки / N. Події надсилаємо не частіше ніж раз на 500 мс,
крім змін стану. До фіксації результату показуємо максимум 99%;
100% означає Completed зі збереженим результатом.

## 5. Збереження та формат результату

- User: id, нормалізована унікальна адреса email, passwordHash, role, createdAt.
- SimulationTask: id, ownerId, вихідні та нормалізовані параметри, solverVersion,
  status, progress, completedSteps, totalSteps, createdAt, startedAt, finishedAt,
  cancellationRequestedAt, workerId, attempt, leaseUntil, version, errorCode.
- SimulationResult: taskId (унікальний), nx, ny, часи кадрів, min/max,
  формат, двійкові кадри. Початково PostgreSQL bytea; великі об'єктні сховища
  потребуватимуть окремого рішення.
- Outbox / Inbox: доставка команд і захист обробки відповідно до механізмів MassTransit.

Часи системних подій — UTC; час симуляції — секунди від 0.
REST-метадані — JSON/camelCase; ідентифікатори — UUID, стани — рядки.
Кадр: Float32 little-endian, Nx*Ny значень, index = j*Nx+i,
x збільшується вправо, y збільшується вгору. Canvas перевертає вісь y.
Клієнт завантажує кадри окремо, не передає повні матриці через SignalR.
Розрахунок залишається double; Float32 використовується для збереження візуалізації.

Фактична кількість кадрів K = min(requestedFrames, N+1).
Крок кадру k = floor(k*N/(K-1)), k = 0..K-1: завжди є початок і фінал,
кроки унікальні. Перевірка розміру: checked(K*Nx*Ny*4) <= 32 MiB.
Часткові кадри не публікуємо як успішний результат скасованої або невдалої задачі.

## 6. Контракти REST API v1

Спільний префікс `/api/v1`. Авторизація JWT Bearer, крім register/login.

| Метод і маршрут | Призначення / успіх |
|---|---|
| POST /auth/register | email, password -> 201; відповідь без passwordHash |
| POST /auth/login | email, password -> 200, accessToken, expiresAt, user |
| GET /auth/me | Поточний користувач -> 200 |
| GET /simulation-limits | Чинні обмеження та підтримувані умови -> 200 |
| POST /simulations/validate | Перевірка без створення -> 200, нормалізовані параметри й оцінки |
| POST /simulations | Створення -> 202, id, status, statusUrl; заголовок Location |
| GET /simulations | Власна історія; page >= 1, pageSize 1..50, status? -> 200 |
| GET /simulations/{id} | Стан, параметри, прогрес, оцінка очікування -> 200 |
| POST /simulations/{id}/cancel | Queued -> 200 Cancelled; Running/Cancelling -> 202 |
| GET /simulations/{id}/result | Метадані готового результату -> 200 |
| GET /simulations/{id}/frames/{index} | Двійковий кадр, application/octet-stream -> 200 |
| DELETE /simulations/{id} | Видалення остаточної задачі та результатів -> 204 |
| GET /admin/overview | Тільки Admin: черга, задачі, Worker, навантаження -> 200 |

Повторне скасування остаточної задачі повертає 200 з її поточним станом.
Видалення активної задачі або читання ще неготового результату -> 409.
Список задач сортується за createdAt DESC, id DESC і повертає items, page,
pageSize, totalCount. Неіснуючий індекс кадру -> 404.

Поля створення та validate (однакова схема):

```json
{
  "name": "Перенесення гаусової плями",
  "domain": { "lengthX": 100, "lengthY": 100, "nodesX": 101, "nodesY": 101 },
  "transport": { "velocityX": 0.5, "velocityY": 0.1, "diffusion": 0.1 },
  "time": { "durationSeconds": 60, "timeStepSeconds": null },
  "initialCondition": { "peak": 1, "centerX": 25, "centerY": 50, "sigma": 5 },
  "boundaryCondition": "ZeroDirichlet",
  "requestedFrames": 16
}
```

Усі поля обов'язкові, крім nullable timeStepSeconds; name — 1..100 символів
після trim. Для першої версії дозволено лише ZeroDirichlet.
Validate повертає dx, dy, effectiveTimeStepSeconds, totalSteps,
estimatedCellUpdates, frameCount, estimatedResultBytes і warnings.
Створення завжди повторює валідацію; validate не резервує квоту.
Початкова оцінка секунд виконання/очікування може бути null до накопичення вимірів.

Створення підтримує заголовок Idempotency-Key (UUID): зберігаємо унікальність
(ownerId, key), хеш запиту й taskId на 24 години. Повтор із тим самим вмістом
повертає ту саму задачу; з іншим вмістом -> 409. Резервування ключа, квоти,
задача та outbox-команда фіксуються однією транзакцією.

Помилки — ProblemDetails з code, traceId, а для валідації — errors за полями:
400 — некоректні параметри/нестійка схема/ліміт складності;
401 — немає чинного токена; 403 — немає ролі Admin;
404 — задача відсутня або належить іншому користувачу;
409 — конфлікт стану/ключа; 429 — перевищення квоти задач або частоти;
503 — інфраструктура не готова прийняти нову задачу.
Деталі внутрішніх винятків клієнту не розкриваються.

## 7. Контракти повідомлень і SignalR

Контракти не передають EF-сутності або Core-буфери.
Envelope: messageId, correlationId (= taskId), occurredAtUtc, schemaVersion = 1.

| Повідомлення | Дані |
|---|---|
| RunSimulationCommand | taskId; Worker читає незмінні нормалізовані параметри з БД |
| CancelSimulationCommand | taskId; прискорює перевірку збереженого запиту скасування |
| SimulationProgressEvent | taskId, attempt, version, status, completedSteps, totalSteps, progressPercent |
| SimulationFinishedEvent | taskId, attempt, version, status, errorCode?; без двійкових кадрів |

RunSimulationCommand надсилається у спільну чергу competing consumers.
CancelSimulationCommand доставляється через fan-out до зацікавлених Worker,
а не до випадкового споживача черги запуску. Успіх і результат спочатку
фіксуються в БД разом із outbox-подією, потім публікуються.

Hub: `/hubs/simulations`. Методи Subscribe(taskId), Unsubscribe(taskId).
Сервер перевіряє власника до вступу до групи. Подія клієнту:
SimulationUpdated з taskId, version, status, progressPercent, completedSteps,
totalSteps, estimatedWaitSeconds?, errorCode?. Версія монотонна в межах задачі;
події зі старішою/рівною версією клієнт ігнорує.
Після reconnect клієнт повторно підписується й читає REST-стан.
SignalR не є сховищем історії; при недоступності використовується REST polling.

## 8. Архітектура та залежності

```text
Browser -> YARP -> WebApi A / WebApi B
                    |  |       |
                    |  +-------+--> Redis (SignalR backplane, cache)
                    +-------------> PostgreSQL (users, tasks, results, outbox)
                    +-------------> RabbitMQ -> Worker A / Worker B
                                                 |           |
                                                 +-- Core ---+
                                                 +-- PostgreSQL
                                                 +-- RabbitMQ (events)
RabbitMQ events -> WebApi notification consumers -> SignalR -> Browser
```

Рекомендована схема notification consumers: окрема тимчасова subscription-черга
на API, подію обробляє лише локальний HubLifetimeManager (без повторної
публікації через backplane); або одна спільна consumer-черга і звичайний
IHubContext із Redis backplane. Для першої реалізації обираємо другий варіант,
щоб не множити однакові сповіщення.

Залежності проєктів:
- Core -> жоден інший проєкт; домен, solver, інтерфейси зовнішніх операцій.
- Contracts -> жоден інший проєкт; wire DTO, enums, commands/events.
- Infrastructure -> Core; EF, Redis, Docker-адаптери. Залежність від Contracts
  додаємо лише якщо тут розміщуватимемо outbox-адаптер конкретних повідомлень.
- WebApi -> Core, Contracts, Infrastructure; auth, endpoints, Hub, notifications.
- Worker -> Core, Contracts, Infrastructure; consumers, computation orchestration.
- LoadBalancer -> жоден бізнес-проєкт; YARP routes, health checks, TLS.
- Client -> HTTP/SignalR-контракти; без прямого доступу до БД і брокера.

Зворотні залежності заборонені. Domain не використовує wire DTO:
мапінг явний у WebApi/Worker. Базовий solver не звертається до БД або мережі.
Важкі обчислення виконуються лише Worker.
Два API самі по собі не доводять розподіл обчислень: демонструємо також
workerId і паралельне виконання різних задач двома Worker.

Redis — допоміжний сервіс, PostgreSQL — остаточне джерело стану.
Для стандартного SignalR negotiation у YARP потрібна session affinity навіть
за Redis backplane: [Microsoft](https://learn.microsoft.com/en-us/aspnet/core/signalr/scale).
API stateless щодо бізнес-даних; тимчасові SignalR-з'єднання локальні.
Автомасштабування виконує один окремий керуючий процес, не кожен HTTP-запит;
мінімум 2 Worker, початковий максимум 4, із cooldown і graceful drain.
Детальні правила та доступ до Docker API — етап 9.

## 9. Критерії приймання наступних етапів

1. Solver: нульове поле залишається нульовим; за ux=uy=D=0 поле незмінне;
   знаки швидкості працюють у чотирьох напрямках; нестійкий крок відхиляється.
2. Чисельна точність: порівняння з гаусовим розв'язком на великій області
   до впливу меж; згущення сітки зменшує похибку; Upwind має чисельну дифузію.
   Додатковий тест сталої концентрації потребує узгодженої тестової межової умови,
   він не застосовується до ненульового поля з ZeroDirichlet.
3. API: чужі задачі недоступні; одночасні POST не обходять квоти;
   повторний ключ не створює дубль; неготовий результат не видається як готовий.
4. Worker: дублі повідомлень не дублюють результат; падіння відновлюється в межах
   ліміту спроб; старий Worker не перезаписує результат нової спроби.
5. Скасування: працює через будь-який API, у черзі й під час роботи;
   гонка з фіналізацією має один узгоджений результат.
6. Frontend: reconnect відновлює актуальний стан; Canvas правильно орієнтує осі;
   історія переживає перезапуск процесів.
7. Розподіл: два API обслуговують запити; два Worker виконують різні задачі;
   втрата одного екземпляра не робить всю систему недоступною.
8. Додаткові бали: queued-стан і приблизне очікування, обмежене масштабування,
   доступна лише адміністратору панель стану.

## 10. Що вирішено і що ще перевірити

Модель, одиниці, граничні умови, схема, API, формати і напрямки залежностей
визначені цим документом. Числові ліміти є початковою політикою.
На етапі 2 перевіряємо сумісність/умови використання встановлених пакетів,
фіксуємо версії й перевіряємо запуск середовища. На етапі 3 — точність,
пам'ять і час. На етапі 5 — точні параметри retries, heartbeat і lease.
До перевірки Docker сервісів поточне середовище не вважається запущеним.
